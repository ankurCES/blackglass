# Blackglass sub-plan 3 — Tauri UI shell + Gate 3 real implementation

**Status:** Design, awaiting user review
**Date:** 2026-06-03
**Sub-plan:** 3 of 4 (sub-plans 1-2 complete; 3+ deferred)
**Slice:** 3α (Tauri shell + IPC bridge) + 3β (confirmation modal + Gate 3 real implementation)

## 1. Scope

This sub-plan ships the **first** operator-facing UI for blackglass and turns
Gate 3 from an `AllowAll` stub into a real asynchronous confirmation flow.
Everything else in spec §6 (audit log browser, engagement workspace, AI session
view, prompt-injection review, tools catalog, settings, kill switches) is
**deferred** to later sub-plans.

In scope:

- A new `crates/ui/` Tauri 2.x desktop app (Svelte 5 + Vite + Tailwind).
- A second Unix socket on `blackglass-core` — the **operator socket** —
  separate from the existing **runtime socket** that MCP servers use.
- A real async `Gate3` implementation that round-trips through the operator
  socket: the chokepoint asks the Tauri app to confirm, the Tauri app shows
  a modal, the operator clicks Allow / Deny / Allow & Remember, the result
  goes back to the chokepoint.
- Top banner (§6.3) and left rail (§6.4) — minimal but real.
- Confirmation modal (§6.5) — the only fully-wired view in this sub-plan.
- Honest "coming in sub-plan N" placeholders for the other 4 left-rail views.
- 7 new core-side unit tests covering every branch of the Gate 3 wire format.
- 6 new ADRs (0007-0012) recording the design decisions.

Out of scope:

- Polkit, root-UID core, AppArmor profile path, capability drops. (§2.2 spec
  trust topology. Deferred to a packaging sub-plan.)
- `.deb` packaging, polkit policy, udev rules, cosign signing. (§7. Deferred.)
- Audit log browser, engagement workspace, AI session view, prompt-injection
  review, tools catalog, settings, kill switches. (§6.6 - §6.12. Deferred to
  3γ, 3δ, 3ε, 3ζ.)
- Tauri-window integration test (WebDriver / headless WebKit). Deferred.
- Fuzzing the operator-socket protocol. (§2.4. Deferred.)
- The Python sidecar. (§2.3. Deferred.)
- Per-tool metadata for the modal (estimated time, safety notes). Stubbed
  in the payload; see §6.5 below.

## 2. Architecture

```
┌────────────────────────────────────────────────────────────────────────┐
│  operator (UID 1000)                                                   │
│                                                                        │
│  ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐   │
│  │  blackglass-ui   │   │ blackglass-core  │   │ blackglass-mcp-* │   │
│  │  (Tauri 2 app)   │   │ (chokepoint)     │   │ (MCP servers)    │   │
│  │  Svelte 5        │   │                  │   │                  │   │
│  │                  │   │  bind 2 sockets: │   │                  │   │
│  │  ↕ operator.sock │   │   • operator.sock│   │  ↕ runtime.sock  │   │
│  │   (Tauri↔core)   │   │   • runtime.sock │   │                  │   │
│  │                  │   │                  │   │                  │   │
│  │                  │   │  Gate 1+2 real   │   │                  │   │
│  │                  │   │  Gate 3 NEW      │   │                  │   │
│  │                  │   │  Gate 4 real     │   │                  │   │
│  └──────────────────┘   └──────────────────┘   └──────────────────┘   │
│                                                                        │
│  both sockets in ~/.local/share/blackglass/                             │
│  tokens in 0600 file, owned by operator UID                             │
└────────────────────────────────────────────────────────────────────────┘
```

**Process model (dev mode).** Tauri app and `blackglass-core` both run as
the operator UID. No polkit prompt, no AppArmor, no capability drops. This
matches the current state of `blackglass-core` (sub-plans 1-2) and avoids
the need for a real Linux box with polkit just to run the dev build. The
spec's split-UID production topology (§2.2) is reachable later via a
packaging sub-plan. (See ADR 0008.)

**Wire format.** Two Unix sockets:

| Socket | Path | Who connects | Protocol |
|---|---|---|---|
| `operator.sock` | `~/.local/share/blackglass/operator.sock` | Tauri app (one connection) | Custom JSON-RPC + server-pushed events |
| `runtime.sock` | `~/.local/share/blackglass/runtime.sock` | MCP servers, CLI | Existing JSON-RPC from sub-plan 1 (unchanged) |

Both sockets require the same 0600 token from
`~/.local/share/blackglass/operator.token`, generated by `blackglass init`.
(Re-using one token simplifies v1; per-socket tokens are a v1.1 thing.)

The two-socket split is the load-bearing design choice. It makes "is the
Tauri app present?" trivial (operator socket is open = yes), avoids
flooding MCP servers with `confirm.request` events, and matches the
spec's trust topology (§2.2: "Human UI" and "MCP servers" are distinct
rows). The spec's wording "all three tiers talk the same JSON-RPC 2.0
dialect" still holds — same dialect, just over two transports. (See ADR
0009.)

## 4. Data flow

### 4.1 Initial connect (Tauri app ↔ core, on startup)

```
Tauri app (Tauri Rust side)        Core (operator socket)
  |                                       |
  |--- connect + auth(token) ------------>|
  |<-- ok=true (auth succeeded) ----------|
  |                                       |
  |--- core.status(id=0) ---------------->|
  |<-- {profile, engagement, scope_       |
  |     counts, time_remaining,           |
  |     awaiting_confirm_count,           |
  |     session_state} -------------------|
  |                                       |
  |  (Tauri side stores in core.svelte.ts |
  |   as $state; views re-render)         |
```

### 4.2 Confirmation flow (MCP server → core → Tauri app → core → MCP server)

```
MCP server (runtime socket)        Core (chokepoint)            Tauri app (operator socket)
  |                                    |                                |
  |--- execute_action ---------------->|                                |
  |   {class: "destructive"}           |                                |
  |                                    | Gate 1: ok                     |
  |                                    | Gate 2: ok                     |
  |                                    | Gate 3: needs confirmation     |
  |                                    | emit OperatorConfirmationRequested
  |                                    | (audit event)                  |
  |                                    |                                |
  |                                    |--- (server-pushed event) ----->|
  |                                    |    confirm.request {           |
  |                                    |      id, request_id, tool,     |
  |                                    |      domain, class, source,    |
  |                                    |      target, action,           |
  |                                    |      deadline_in_ms}           |
  |                                    |                                |
  |                                    |                  [modal shows;  |
  |                                    |                   countdown]    |
  |                                    |                                |
  |                                    |<-- confirm.resolve -----------|
  |                                    |    {id, decision: "allow"}     |
  |                                    |                                |
  |                                    | emit OperatorConfirmationResolved
  |                                    | (audit event)                  |
  |                                    |                                |
  |                                    | Gate 3 -> ok                   |
  |                                    | simulate_execute (still stub)  |
  |                                    | emit ActionExecuted            |
  |<-- {ok: true, result: ...} --------|                                |
```

If the Tauri app is **not connected** when Gate 3 fires: the chokepoint's
`.await` immediately resolves to `ConfirmationOutcome::Disconnected`, which
is treated as deny. Logged as `OperatorConfirmationResolved` with
`decision: "disconnected"`.

If the **15-second countdown** expires: the chokepoint's `.await` resolves
to `ConfirmationOutcome::Timeout` (deny). Logged as `OperatorConfirmationResolved`
with `decision: "timeout"`.

If the Tauri app **disconnects mid-confirmation**: the operator-socket
handler's read loop returns `Err`; the handler finds any pending
confirmations matching that connection and cancels them with reason
`disconnected`.

### 4.3 Wire payload shapes

`core.status` request:
```json
{ "id": 0, "method": "core.status", "params": {} }
```

`core.status` response:
```json
{
  "profile": {
    "name": "analyst",
    "tier": "analyst",
    "allowed_domains": ["core", "osint", "packets", "audit"],
    "allowed_action_classes": ["read_only", "destructive"]
  },
  "engagement": {
    "id": "default",
    "client": "default engagement",
    "window_end": "9999-12-31T00:00:00Z"
  },
  "scope_counts": { "allow": 0, "deny": 0 },
  "time_remaining": {
    "engagement_seconds": 2538840000,
    "session_seconds": null
  },
  "awaiting_confirm_count": 0,
  "session_state": "idle"
}
```

`confirm.request` (server-pushed event on operator socket):
```json
{
  "id": "018f3b1c-7e2a-7c2e-bf3e-1c0a2b3c4d5e",
  "request_id": 42,
  "tool": "nmap_scan",
  "domain": "recon",
  "class": "destructive",
  "source": "ai-session-claude-opus-4",
  "target": "10.10.0.5/24",
  "action": "nmap -sV -p 1-1000 10.10.0.0/24",
  "deadline_in_ms": 15000
}
```

`confirm.resolve` (Tauri → core, on operator socket):
```json
{ "id": 0, "method": "confirm.resolve", "params": {
  "id": "018f3b1c-7e2a-7c2e-bf3e-1c0a2b3c4d5e",
  "decision": "allow"
}}
```

`confirm.resolve` response:
```json
{ "id": 0, "ok": true }
```

Unknown fields in `confirm.request` are ignored on the Tauri side
(forward-compat). Known fields are required.

## 6. Gate 3

### 6.1 The new `Gate3` trait

```rust
#[async_trait]
pub trait Gate3: Send + Sync {
    async fn confirm(&self, req: ActionRequest) -> ConfirmationOutcome;
}

pub enum ConfirmationOutcome {
    Allow,
    AllowAndRemember,
    Deny,
    Timeout,
    Disconnected,
}
```

`AllowAll` is kept for tests only, behind `#[cfg(test)]`. In production,
the chokepoint holds an `Arc<dyn Gate3>` whose concrete type is
`OperatorGate3 { service: Arc<OperatorConfirmationService> }`.

### 6.2 The `OperatorConfirmationService`

Owns:

- The operator socket's accept loop.
- A `HashMap<ConfirmationId, oneshot::Sender<ConfirmationOutcome>>` of
  pending confirmations.
- A `HashMap<ConnectionId, HashSet<ConfirmationId>>` reverse index, so
  that when a connection drops, all its pending confirmations can be
  cancelled.

API used by the chokepoint:

```rust
impl OperatorConfirmationService {
    pub async fn request(&self, req: ActionRequest, timeout: Duration)
        -> ConfirmationOutcome;
}
```

The `request` method:

1. Generates a new `ConfirmationId` (UUID v4).
2. Builds a `confirm.request` payload (§4.3).
3. Broadcasts it to **all** currently-connected operator clients.
4. Starts a `tokio::time::timeout(timeout, oneshot::recv)`.
5. If the timeout fires first, removes the entry from the map and returns
   `ConfirmationOutcome::Timeout`.
6. If the oneshot resolves first (because a `confirm.resolve` came in),
   returns the received outcome.
7. If the **only** connected operator client disconnects while we're waiting,
   the disconnect handler cancels the oneshot with `Disconnected` and we
   return that.

### 6.3 Action-class mapping

| `ActionRequest.action_class` | Gate 3 behavior |
|---|---|
| `read_only` | Auto-allow (no confirmation). |
| `destructive` | Call `OperatorGate3::confirm`. |
| `passive` (future) | Auto-allow. |
| `transmit` (future) | Call `OperatorGate3::confirm` with extended UI (PIN, frequency). |
| anything else | Auto-allow (matches "default-allow" in the absence of a strict mapping). |

The `read_only` / `destructive` split is a v1 simplification. Spec §4.4
mentions a richer class taxonomy; we grow into it in later sub-plans.

### 6.4 Audit events

Two new `EventKind` variants, both in `blackglass-audit`:

```rust
pub enum EventKind {
    // ... existing variants ...
    OperatorConfirmationRequested,
    OperatorConfirmationResolved,
}
```

`OperatorConfirmationRequested` carries:

```json
{
  "confirmation_id": "uuid",
  "request_id": 42,
  "tool": "nmap_scan",
  "domain": "recon",
  "class": "destructive",
  "target": "10.10.0.5/24",
  "source": "ai-session-claude-opus-4"
}
```

`OperatorConfirmationResolved` carries:

```json
{
  "confirmation_id": "uuid",
  "decision": "allow | allow_and_remember | deny | timeout | disconnected | deny_late"
}
```

The 6 `decision` values are kept distinct because the prompt-injection
review page (3ε, deferred) will want to surface "operator clicked Deny"
vs "system timed out" differently.

### 6.5 Per-tool metadata (modal fields)

`Estimated time`, `Estimated output`, `Safety notes` — all metadata fields
shown in the spec's modal are **stubbed** in sub-plan 3. The
`ActionRequest` type does not carry them. The modal renders a "coming in
sub-plan 3γ" line in their place. This is honest: the data flow is real,
the missing fields are reserved in the type, and the per-tool metadata
table is real work for a later sub-plan.

## 7. Error handling

### 7.1 Tauri app side

| Failure | Behavior |
|---|---|
| Tauri app fails to start (deps missing, port in use) | Tauri shows a startup error page. The CLI's `blackglass status` (still on the runtime socket) works as a fallback. |
| Tauri app loses connection to operator socket (core crashed, socket file deleted) | Frontend shows a red banner: "core disconnected — actions cannot run". `core.status` retries every 2s with backoff up to 30s. Reconnects on socket reappearance. |
| `confirm.request` arrives with malformed payload | Log a warning in the Tauri Rust side; drop the event; do not show the modal. |
| `confirm.request` arrives with unknown fields | Ignore unknowns; render the modal with the known fields. |
| User clicks "Deny" after the 15s countdown expires | The chokepoint has already denied on timeout. The late `confirm.resolve` is logged as `OperatorConfirmationResolved` with `decision: "deny_late"` and the audit chain stays valid. The modal closes; no further effect. |

### 7.2 Core side

| Failure | Behavior |
|---|---|
| Operator socket bind fails (path taken) | Core exits with non-zero status; CLI surfaces the error. |
| `execute_action` arrives on runtime socket with `class: "destructive"` but Tauri app is not connected | Deny; emit `OperatorConfirmationResolved` with `decision: "disconnected"`; emit `ActionDenied`. |
| Two `execute_action` requests arrive concurrently, both `destructive` | Each gets its own confirmation; both stack in the right panel (top-down, most recent on top). Chokepoint tasks are independent. If the Tauri app resolves them out of order, the audit log records the resolution in the order the Tauri app sent them, with the matching `id`. |
| 15s timeout fires | Cancel the oneshot; resolve as `Timeout`; emit `OperatorConfirmationResolved` and `ActionDenied`. |
| Tauri app disconnects mid-confirmation | The operator-socket handler's read loop returns `Err`; the handler finds the pending confirmation and cancels it with reason `disconnected`. |
| Tauri app tries to resolve a confirmation that doesn't exist (bad id) | The chokepoint logs a warning, sends `ok: false, error: "unknown confirmation id"`. No audit event. |
| Tauri app tries to resolve a confirmation that already timed out | Same as above; the response is late. |

### 7.3 Audit invariants

- `OperatorConfirmationRequested` is emitted **before** the chokepoint `.await`s.
- `OperatorConfirmationResolved` is emitted **immediately** after the `.await` resolves.
- For denied outcomes (timeout, disconnected, deny button, deny_late),
  `ActionDenied` follows `OperatorConfirmationResolved` in the chain.
- For allowed outcomes, `ActionAllowed` follows `OperatorConfirmationResolved`,
  and `ActionExecuted` follows `ActionAllowed`.
- For `read_only` actions, the chain is unchanged from sub-plan 1:
  `ActionRequested`, `ActionAllowed`, `ActionExecuted` (3 events).
- For `destructive` actions, the chain is 5 events:
  `ActionRequested`, `OperatorConfirmationRequested`,
  `OperatorConfirmationResolved`, `ActionAllowed` (or `ActionDenied`),
  `ActionExecuted` (or no event if denied).
- The sub-plan 1 chokepoint test (3 events, `read_only`) stays as-is. A
  new chokepoint test (5 events, `destructive` with operator allow) is
  added.

## 8. Testing

### 8.1 Core-side unit tests (in `crates/core/tests/`)

7 new tests, all `#[tokio::test]`, all using a helper that stands up a
core with a custom (fast) timeout:

1. `destructive_action_with_operator_allow` — operator connects, receives `confirm.request`, sends `confirm.resolve{decision: "allow"}`, action proceeds. Asserts 5 audit events in correct order.
2. `destructive_action_with_operator_deny` — same, but decision is "deny". Asserts 4 audit events: requested → requested → resolved(deny) → denied.
3. `destructive_action_with_no_operator_connected` — Tauri app never connects. Chokepoint denies immediately. Asserts `decision: "disconnected"`.
4. `destructive_action_times_out_after_15s` — operator connects but never sends `confirm.resolve`. Use a 200ms timeout in test mode. Asserts `decision: "timeout"`.
5. `destructive_action_operator_disconnects_mid_confirmation` — operator connects, receives request, drops the connection. Asserts `decision: "disconnected"`.
6. `two_destructive_actions_concurrently_both_confirmable` — two MCP-server-side `execute_action`s fire; both get confirmations; both are resolvable independently; both complete. Asserts 10 audit events (5+5).
7. `core_status_returns_expected_shape` — operator connects, calls `core.status`, asserts the response payload matches the schema in §4.3.

### 8.2 Tauri Rust-side unit tests (in `crates/ui/src-tauri/src/`)

### 8.4 Manual end-to-end test (not in CI)

1. Start `blackglass-core` in a terminal.
2. Run `cargo tauri dev` in `crates/ui/`. The Tauri window opens; the banner says "connected."
3. From another terminal, run an MCP server that issues a `destructive` action. The modal pops in the Tauri window with a 15s countdown.
4. Click "Allow" — the MCP server's request returns ok, the modal closes, the audit log has the expected 5-event sequence. Verify with `blackglass audit-verify`.
5. Repeat with "Deny", "Allow & Remember", timeout, disconnect.
6. Run `cargo test --workspace` — 100% green.

## 10. ADRs added by this sub-plan

Six new ADRs, all in `docs/decisions/`:

- **0007-tauri-stack.md** — Tauri 2.x + Svelte 5 + Vite + Tailwind; WebKitGTK 4.1 (not 6.0 as spec says; drift noted).
- **0008-dev-mode-operator-uid.md** — Dev mode runs everything as operator UID; polkit/root deferred to a packaging sub-plan.
- **0009-two-socket-ipc.md** — Operator socket + runtime socket. Same JSON-RPC dialect; different transports.
- **0010-gate3-wire-format.md** — Server-pushed `confirm.request` events + Tauri-issued `confirm.resolve` RPCs. UUID v4 confirmation ids. 15s timeout.
- **0011-audit-event-kinds.md** — Adds `OperatorConfirmationRequested` and `OperatorConfirmationResolved` (with 6-value `decision`).
- **0012-dev-build-distribution.md** — `cargo tauri dev` for development; `cargo tauri build` produces a Tauri-app-only bundle; the full `.deb` system package is a later sub-plan.

## 11. Spec drift to flag

Three places where this sub-plan diverges from the design spec; all
intentional and reachable later:

- **§2.2 trust topology.** Spec says core runs as root via polkit. Sub-plan 3 runs everything as operator UID. Reachable via packaging sub-plan.
- **§6.15 WebKitGTK version.** Spec says 6.0. We use 4.1 (Tauri 2 default, Ubuntu 24.04 stock). Spec to be amended.
- **§4.4 action-class taxonomy.** Spec implies a richer set. We use just `read_only` and `destructive` for v1.
